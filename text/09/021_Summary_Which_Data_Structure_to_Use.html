Summary: Which Data Structure to Use?

📺 来源：021 Summary Which Data Structure to Use.en.srt 📂 章节：第 09 章
📌 终点回顾之巅

我们手上已囊括 JavaScript 里的四大基本核弹器：大组 (Array)，对象 (Object)，以及刚入库收割的高精端 图集 (Map) 与 去重洗涤器 (Set)。面对海量奔涌而来的代码业务情境，什么阶段拔什么尺寸的剑，在这里将获得终极梳理。

🎯 数据集的第一岔路口抉择图

每次遇到需要存放一大堆数据的地步，请脑内浮起这个问题：
我是仅仅需要存放一排纯粹孤立的数值连成的线索？ 还是需要把每一根数值旁边都挂靠着有极强描述性意味的文字标牌（挂门牌）？

  • 👉 只是单纯首尾堆砌的值排列 (Simple List)：往左边走进入 Arrays（大组）与 Sets（集合） 阵痛选择台。
  • 👉 带有严格上下溯源名字标牌的抽屉 (Key/Value pairs)：往右走来到 Objects（对象）与 Maps（哈希表图集） 的战场中心。

⚔️ 阵列队列赛道：Array 🆚 Set

选择阵列利刃 使用心法与特性
🗂️ Array (数组大组)
最泛滥最中坚主力存在		 • 当你必须必须维持数据被送入时的先后顺序不容乱动打散！
• 当数据列表里允许并需要收纳多个并排行走的无耻克隆复制体数据。
• 当你后续还要对它施展天花乱坠的大改操盘变形法术 (后面大篇幅学习的一堆 Array 方法)。
🧼 Set (去重洗碗池)
专情纯粹的高速杀器		 • 当你绝无法容忍一丁点重复病菌残体存在于系统时！
• 当你要最极速压榨性能。在极其厚重的巨海数据里，要删除某个东西、搜索是否存在它，Set 会比 Array 甚至狂甩出 10 倍的光速响应断层差。

⚔️ 保险箱键值抽屉赛道：Object 🆚 Map

这绝对是重头戏。由于 JS 前十多年的发展历史只有畸形霸场的 Object，所以一直拿它疯狂客串键值缓存库。但是在拥有 Map 后的新纪元，天枰被血腥逆转。

柜体选型决战 统治与退场理由
📦 Object (古老地基霸主) 继续留用的护体金牌：
• 写起来写烂了闭着眼都会，就是简单粗暴直接点出 obj.name 与 obj['age'] 的极速穿透提取快感。
• 必须内挂捆绑各种活动功能函数方法 (Methods) 时！ Object 内带天生 this 光环机制指路自己，但 Map 直接断代此能力。
• 与大后端 API 传输返回 JSON 的天然适配转换（后续会提）。
🗺️ Map (全能超维图解柜) 夺权上位的顶级理由：
• 完全不受制于只许传字符串拉胯当 Key 钥匙的诅咒约束锁链！万物皆可为键！
• 自生骨血兼容 Iterable，自带 for-of 和 .size。而笨重的 Object 每一次都要靠别人破相借尸还魂去转。
• 极端大型并极度频繁挂拆门牌与加进加出 Key 时候，引擎底下有着远高于对象的底层狂暴加速优越感性能。

🔌 彩蛋扩展认知：Web API 与 JSON 的绝对领海归宿

几乎 99% 从后场外部真实世界上获取的天外飞仙 Web 数据请求，砸扁到我们前端机器里时都是长成一幅 阵列列车厢内部包裹着无数只小对象盒子的 JSON 格式体 (Array of Objects) 的混合拼接骨架。

比如 [ {name:'Pizza', price:10}, {name:'Pasta', price:15} ]。虽然我们知道 Map 性能狂霸，但我们极少吃饱了撑了费力气手操把这种飞来的天然 JSON 客船全给拆装倒腾改写为 Map 挂载架构。依然还是大面积使用传统天生相合贴合的 Object 骨架作为承接器去消化它。只有极其复杂的偏方黑科技功能模块内，才会专程调用建图。
