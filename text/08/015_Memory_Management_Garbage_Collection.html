Memory Management: Garbage Collection (垃圾回收机制)

📺 来源：015 Memory Management Garbage Collection.en.srt 📂 章节：第 08 章

🎯 概述

跟 C 语言那种需要手动申请和释放内存的底层语言不同，JavaScript 是一门高度自动化的语言。它内置了一个“清洁工”——垃圾回收器 (Garbage Collector)。它会自动在后台打扫堆内存 (Heap) 中那些不再被使用的对象。本节我们将探讨这个清洁工是如何判断垃圾的，以及身为开发者，我们如何避免因为代码写得太烂而导致它扫不动垃圾（即内存泄漏现象）。

1. 核心算法：标记-清除算法 (Mark and Sweep)

几乎所有现代 JavaScript 引擎（包括 V8）处理垃圾回收的核心思路都是 “标记-清除算法” (Mark and Sweep Algorithm)。它的名字极其形象，分为两大阶段：

第一阶段：标记 (Mark Phase) —— 谁还活着？

清洁工会从几棵“根节点 (Roots)”出发，顺藤摸瓜寻找所有被引用的对象。只要能被顺着线找到的对象，就会被标记为“活着 (Alive)”。那什么算是 Root 呢？

  • 全局执行上下文 (Global Execution Context)（比如顶层 window 对象引用的东西）
  • 当前调用栈里所有存活的局部变量
  • 挂载着的事件监听器 (Event Listeners) 和还在倒计时的定时器 (Timers)
  • 活跃的闭包 (Closures)

第二阶段：清除 (Sweep Phase) —— 销毁死者

一旦标记阶段结束，清洁工就会无情地把堆里所有没有被标记（打不上“Alive”标签）的对象，如上图红色的 对象 C，当作垃圾给**抹除掉**。内存空间因此被腾出，为后续新建的其他对象让出跑道。

💡 重要概念： 这个清除过程是完全自动化且黑盒的！你无法在 JS 代码里命令引擎“现在立刻给我扫垃圾”。引擎会根据内存压力、空闲时间等智能调度触发时机。

2. 警惕：内存泄漏 (Memory Leaks) 的幽灵

垃圾收集器看起来很神，但它也不是万能的。如果我们代码写得不规范，强行死死拽着某个对象不放，垃圾收集器就只能看着它叹气而不敢清理。这就叫 内存泄漏 (Memory Leak)。

打个比方：这就像是你家里放了一个坏掉的大冰箱，虽然你已经不用它了，但你偏偏用锁把它和墙根连起来了。清洁工一来，一看有锁（有引用），只能摇头走人。久而久之，你的房子（内存）就被这种废物塞满了，最终导致网页卡顿甚至崩溃。

🔪 导致内存泄漏的几大元凶（实战防坑指南）：

  1. 忘记清理的定时器 (Timers)：
    如果你用 setInterval 创建了一个轮询，并在里面引用了一个巨大无比的数组。只要你不写 clearInterval，这个定时器就会作为 Root 永远活着，那那个巨大数组也就永无见天之日，永远霸占内存。
  2. 游荡的事件监听器 (Event Listeners)：
    比如在单页应用 (SPA) 中，给某个 DOM 元素绑了 addEventListener，但当这个 UI 组件被卸载时，你忘记调 removeEventListener。那些回调函数里的对象引用将阴魂不散。
  3. 滥用全局变量 (Global Variables)：
    全局变量挂靠在 window 这个最强的 Root 上。它永远都不会被垃圾回收。如果你把大量中间运算的数据随手挂载到全局变量上，它们会陪着应用走到生命终点。

🧪 学习验证

1. 我们可不可以在 JavaScript 里写个类似 `GC.run()` 的代码，强制引擎在页面卡顿的时候立刻执行垃圾回收腾出内存？
A) 不可以。JavaScript 是全自动内存管理的，开发者没有任何 API 可以显式控制或触发垃圾回收过程。
B) 可以。使用 `delete objectName` 就可以直接命令引擎清理对象。
正确答案：A。这也是高级语言的特性。delete 关键字只能切断对象上的某个属性，但无法指挥 GC。清理时机全凭 V8 引擎自己决定。

2. 以下哪个场景最容易引发致命的“内存泄漏”？
A) 在 function 内部定义了海量的局部 let 变量。
B) 把几百 MB 的用户行为日志数组，挂载到了 window.globalLogs 属性上，且页面始终不刷新。
正确答案：B。局部变量会随执行上下文的弹出而瞬间进入“失联”状态，被下一次 GC 完美回收（A属于非常健康的表现）。但 B 挂载在了全局 Root 上，只要不关闭标签页，这几百 MB 的垃圾将永垂不朽。
