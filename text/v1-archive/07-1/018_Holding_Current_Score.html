Holding Current Score (保留分数与胜利判定)

📺 来源：018 Holding Current Score.en.srt 📂 章节：第 07 章

上节课我们见识到了由于 activePlayer 是 0 和 1 带来的 HTML ID 映射威力。那对于玩家各自独立沉淀的总分 (Total Score)，我们能怎么存呢？

1. 数组大翻身：多玩家数据装载

与其去建立两个割裂的散装变量 let score0 = 0; let score1 = 0;，更好的做法是把它们塞进一个只有两个元素的数组里：

const scores = [0, 0]; // 0 号房是玩家1总分；1 号房是玩家2总分

这样一来，当我们需要给当前活动玩家加分时，只要写 scores[activePlayer] += currentScore; 即可！你又一次体会到了 0/1 这种布尔系索引值配合数组带来的魔法穿透力。

2. Hold 按钮：落袋为安与夺冠判定

当玩家见好就收，不愿承担爆退风险时，就会点击 "Hold" (保留/入库) 按钮。这会触发一系列连锁操作：

btnHold.addEventListener('click', function() {
  // 1. 把当前的本回合池子里的分，倾倒进全局总分数组里的专属房间
  scores[activePlayer] += currentScore;
  
  // 2. 刷在屏幕上对应的那个总分大字上 (利用模板字符串抓取)
  document.getElementById(`score--${activePlayer}`).textContent = scores[activePlayer];
  
  // 3. 检查他是否赢了比赛 (>= 100 分)
  if (scores[activePlayer] >= 100) {
    // 赢了！游戏结束！颁发黑榜！
    document.querySelector(`.player--${activePlayer}`).classList.add('player--winner');
    // 把之前指示他正在活动的高亮类名去掉，否则两个颜色会打架
    document.querySelector(`.player--${activePlayer}`).classList.remove('player--active');
  } else {
    // 还没赢，只不过是该交涉换人了
    switchPlayer(); // 把上一节的那一坨脱衣服换人代码扔进一个函数里调用
  }
});

3. 高级架构：State Variable (状态守卫变量)

此时存在一个极其弱智的 Bug：一名玩家分数冲破了 100 并且屏幕背景都已经成了黑金色宣告游戏胜利了，此时你如果继续手贱去点击 Roll 骰子按钮，游戏竟然还能不知疲倦地投出新数字、疯狂累加分数甚至疯狂切换回合！

因为计算机就像是一个没有记忆的纯情少男。你虽然用 CSS 给界面染了颜色画上了句号，但你给它绑定的 click 事件依旧坚守岗位，来者不拒。

专业的游戏与电商后端，都会使用一种叫做 State Variable (状态守卫变量) 来作为整个中枢的总闸。这通常是一个布尔值 (Boolean)：

// 在代码最顶部，游戏的大闸：默认通电开启
let playing = true; 

btnRoll.addEventListener('click', function() {
  // 只有当大闸通着电时，里面的机器才允许转动！
  if (playing) {
    // ...掷骰子的一百多行代码
  }
});

btnHold.addEventListener('click', function() {
  if (playing) {
    // ...加分并判断输赢的代码
    if (scores[activePlayer] >= 100) {
      // 🏆 有人赢了！拉闸断电！
      playing = false; 
    }
  }
});

🔧 状态变量的至高哲学：
`let playing = true;` 是一种心智模型，它是对真实世界业务状态的数字化映射。
你不能指望机器去读你的 CSS 样式来推测游戏是否结束；你必须在内存中留存一个“开关”。这也就是为什么在 React/Vue 中，万物皆“状态驱动视图”的底层启蒙！

至此，我们完成了《猪骰子》对决的最核心骨架，它已经是一套滴水不漏的战斗引擎。下一节，我们将以“New Game (新游戏)”按钮为契机收尾！

🧪 学习验证

1. 关于防止“游戏结束后还能点按钮”的 Bug，为什么我们不推荐在有人赢了之后去执行 `btnRoll.removeEventListener('click', ...)`，而是采用声明 `let playing = true` 布尔开关的做法？
A) 因为使用 bool 状态变量 (State Variable) 是业界标准的“状态决定数据流”思想，代码更具拓展性。如果以后加了 10 个按钮，拉下 `playing = false` 总闸就能瞬间瘫痪所有的业务逻辑，而无需挨个去强行解绑 Listener。
B) 因为 JavaScript根本就不支持从 DOM 身上移除事件监听器。
👍 正确！ 解析：虽然能依靠 removeEventListener 解绑，但在现代前端工程学中，我们倾向于“让状态(Data)做主宰”，界面行为只是一层壳。拉下总闸，所有防线一同关闭，这才是干净健壮的架构。
