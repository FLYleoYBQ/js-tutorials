Variable Environment: Hoisting and The TDZ (变量提升与暂时性死区)

📺 来源：008 Variable Environment Hoisting and The TDZ.en.srt 📂 章节：第 08 章

🎯 概述

JavaScript 中有一种长期存在、让无数新手困惑甚至抓狂的机制——变量怎么能在声明之前就使用呢？ 这种现象叫做 变量提升 (Hoisting)。本小节我们将剖析 Hoisting 的本质，以及 ES6 是如何引入 暂时性死区 (TDZ) 来挽救这个历史遗留错误的。

1. 什么是变量提升 (Hoisting)？

很多简单的教程会告诉你："Hoisting 就是 JS 引擎施展魔法，把所有的变量声明神不知鬼不觉地移动到了代码的最顶端"。虽然表面看起来如此，但在幕后并非如此。

真实的原理发生在我们在前面学到的“执行上下文创建阶段 (Creation Phase)”。在正儿八经执行代码之前，引擎会先“扫描”一遍全盘代码，把所有要用的变量名字提前注册进 变量环境 (Variable Environment) 中。

大杀器：JS 中各类声明的提升表现总览（重要考点）

声明方式 是否被提升？(Hoisted?) 提升后的初始值 作用域类型
function (函数声明) ✅ 是的 实际的函数体 (可在声明前安全调用) 块级作用域 (严格模式下)
var 变量 ✅ 是的 undefined (极易引发隐蔽的 Bug!) 函数作用域
let / const 变量 ❌ 否 (技术上提升了，但不能用) Uninitialized (未初始化) -> 报错 块级作用域
函数表达式 & 箭头函数 取决于它是用 var 还是 let/const 声明的，行为等同于普通变量。

🚨 万恶之源 var：如果你在 var x = 10; 这行代码的上一行，去 console.log(x)。你不会像其他语言那样得到报错，而是会得到一个 undefined！这是极度危险的，因为程序会带着一个半成品状态继续运算下去，导致灾难性的后果。

2. 暂时性死区 (Temporal Dead Zone, TDZ)

为了擦亮 var 犯下的错，ES6 设计者引入了 let 和 const，并附赠了 暂时性死区 (TDZ) 机制。


const myName = 'Jonas';

if (myName === 'Jonas') {
    // -------------------------
    // ☠️ TDZ 死亡地带开始
    // console.log(job); -> ReferenceError: Cannot access 'job' before initialization
    // ☠️ TDZ 死亡地带依然在持续...
    // -------------------------
    const job = 'teacher'; // ✅ TDZ 在此行结束，变量诞生！
    
    console.log(job); // 正常输出 'teacher'
}

TDZ 存在的两大意义是什么？

  1. 防弹衣（更容易发现 Bug）：和 var 悄悄咪咪给个 undefined 不同，如果你敢在 TDZ 区域内触碰 let/const 变量，引擎会毫不留情地当面扇你一巴掌（抛出 ReferenceError 异常）。这迫使你养成良好的习惯：**先声明后使用**。
  2. 保卫 const 的尊严：const 变量是常量，一旦定格就终生不可更改。如果它像 var 那样被提升为 undefined，那它后来怎么被赋予真正的常量值呢？为了让常量名副其实，它必须在声明的那一刻才被赋予生命。

💡 拓展阅读：既然提升(Hoisting) 这么扯淡，为什么 JS 的造物主 Brendan Eich 当初要发明它呢？这是因为他想让开发者实现相互递归 (Mutual Recursion)——即函数 A 可以调用底下的 函数 B，函数 B 又能调用上方的 函数 A。为了让函数能被无序散落并随意调用，引擎才搞出了先横扫一圈“提升”所有函数声明的设计。只是顺手把 var 也给波及了进去了而已。

🧪 学习验证

1. 关于箭头函数的变量提升，以下哪种说法是正确的？
A) 只要是函数，无论哪种形式，都会被整体提升，可以在上面随便调用。
B) 箭头函数本质上是被赋值给一个变量的，所以提升的表现完全取决于它是用 var 还是 const/let 声明的。
正确答案：B。const calcAge = arg => arg * 2; 这个写法本质是声明一个 const 变量！在这个变量正式初始化完毕前，调用它是会触发 TDZ 报错的。

2. 为什么在 ES6 及更高版本中，我们绝对应该避免使用 `var`？
A) 因为 var 声明的变量会拖慢引擎的速度。
B) var 不仅无视块级作用域(甚至穿透 if/for)，提升时还会初始化为不安全的 undefined。
正确答案：B。var 的作用域泄露和不报错的提升表现，是以前 JS 大型项目极难调试的元凶。永远拥抱 let/const。
