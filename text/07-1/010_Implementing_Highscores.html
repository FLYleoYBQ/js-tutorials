Implementing Highscores (实现历史最高分)

📺 来源：010 Implementing Highscores.en.srt 📂 章节：第 07 章

上节课我们费了很大功夫实现了不刷新浏览器的 .again 重置功能。现在它的价值体现出来了：因为浏览器不刷新，我们在 JavaScript 中记录的全局变量就不会丢失！

利用这个机制，我们就能实现这部分代码的最后一块拼图：记录并保持最高分 (Highscore)。

1. 最高分逻辑拆解

就像维护生命值 score 一样，我们需要在代码顶端建立一个新的 状态变量 (State Variable)：

let score = 20;
let highscore = 0; // 游戏刚打开时，历史最高分初始为 0

何时去更新这个 highscore？
答案显而易见：只有当玩家猜中数字（胜利）的时候，才有必要触发最高分的结算。

怎么结算？
很简单，在胜利那一刻，拿玩家这局打出的分 score，去和历史最高分 highscore 比一比。如果这把分更高，那么历史最高分的王座就换人坐了。

2. 绑定到代码中

让我们把这段简单的逻辑实装到 'click' 监听器的胜利分支 (if (guess === secretNumber)) 中：

else if (guess === secretNumber) {
  // ... 之前写过的变绿、变宽等样式代码

  // 结算最高分
  if (score > highscore) {
    highscore = score; // 霸占王座
    
    // 把新的最高分印到页面上对应的 DOM 元素里
    document.querySelector('.highscore').textContent = highscore;
  }
}

💡 状态持久化的证明：
当你赢下一局后并按 Again 按钮时：我们在上一节写的重置代码里，**并没有**去动 highscore 变量，甚至都没有去重置屏幕右上角 .highscore 这个 DOM 里的数字。
这就是为什么重新开始游戏后，最高分依然金光闪闪地挂在那里的原因。它“幸存”下来了！

3. 游戏的闭环

至此，我们已经完整开发出了一个基于浏览器的微型游戏，并且实现了：

  • 捕获用户的输入框数据
  • 处理非法格式 (空输入)
  • 核心业务逻辑判断 (猜大、猜小、猜中)
  • 生命值状态管理与扣除
  • DOM 内连样式的动态修改
  • 非刷新式的状态重置 (再来一局)
  • 跨局持久化状态管理 (最高分记录)

太棒了，恭喜你独立构建出了人生中第一个具备完整交互与生命周期的 Web 游戏！

然而，作为专业的开发者，我们的工作不仅仅是“让代码跑起来”。如果你仔细观察目前的完整代码，你会发现当“猜大”和“猜小”的时候，我们写了两坨几乎一模一样的长代码...
在下一节，我们将学习高级工程师的必备素养：重构 (Refactoring) 与 DRY 原则。

🧪 学习验证

1. 为什么我们要把 `let highscore = 0;` 写在事件监听器函数的外面（代码的顶端）？
A) 因为如果写在 `addEventListener` 包裹的函数里面，那么每次玩家点击"Check"按钮时，最高分都会被重新强行初始化为 0，从而无法积累跨回合的数据。
B) 因为 `let` 不能在函数里面声明。
👍 正确！ 解析：这就是“作用域 (Scope)”与“生命周期”的核心概念。写在外面的变量，伴随整个网页存活，能跨越多次点击；写在事件处理函数里的变量，是“一次性”的，每次点击都会被销毁重建。要积累历史数据，必须建在外面！
